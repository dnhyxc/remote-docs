# 资源库词条预取并发：窗口分块 + 限并发异步映射

> **路径已收口**：本文引用的 `library/hooks/useLibraryWordsList.ts` 已在本轮重命名为 `hooks/useEnglishLearningList.ts`，工具函数从 `library/utils/` 上移到 `utils/`。完整变更见 [英语学习列表模块收口.md](./英语学习列表模块收口.md)。

> 解决「续读很深（比如上次读到第 3000 条）」时，首屏一次性把 0→3100 条**全部预取**会产生 3～31 个 HTTP 请求（视 pageSize），瞬间打满浏览器连接池、前面的请求还排队，导致首屏等很久。  
> 方案：把 [0, end) 区间按后端 chunk 上限（1000）切片成「尽量少」的分页请求，并用通用并发池 `mapWithConcurrency` 控制同时进行的请求数（默认 3），在 HTTP/2 多路复用与单库不拥塞之间取平衡。  
> 延伸阅读：[资源库列表单向虚拟滚动.md](./资源库列表单向虚拟滚动.md)（调用方 Hook：预取续读窗口）、[资源库收藏状态分页查询.md](./资源库收藏状态分页查询.md)（收藏状态也复用此工具做并发分块）。

## 1. 背景与目标

### 1.1 问题：深度续读场景请求过多

后端分页 limit 上限提到 1000 之前，单次最多 200。如果续读 offset 是 3000、pageSize = 100，预取 0→3100 共 31 页才能把窗口填满。

串行 31 次请求（每次 ~80ms RTT）：总耗时 ≥ 2.5s，用户看到 Loading 很久。
不加限制并发 31 次请求：瞬间耗尽 HTTP/1.1 浏览器 6 连接上限或 HTTP/2 服务端并发限制，反而造成尾部排队。

### 1.2 目标

| 目标 | 说明 |
| --- | --- |
| 尽量少次 HTTP | 每块尽量拉满 1000，把 31 次砍到 4 次 |
| 限并发 | 避免瞬间打满连接；默认 3 并发（HTTP/2 舒适区） |
| 通用复用 | 分块函数同时供「预取窗口 [0, end)」和「收藏状态增量 [from, to)」两种范围形态使用 |
| 顺序无关但结果有序 | 并发执行不保证顺序，但返回结果数组要和入参数组下标一一对应 |

## 3. 实现思路

### 3.1 两种范围形态

| 函数 | 语义 | 典型场景 |
| --- | --- | --- |
| `buildLibraryPrefetchChunks(resumeOffset, pageSize)` | **从 0 开始**，确保覆盖 `[0, max(pageSize, resumeOffset+pageSize))` | 进库时预取续读窗口：即使 resumeOffset=0 也至少取 1 页（pageSize） |
| `buildLibraryRangeChunks(fromOffset, toExclusive)` | **任意 [from, to)**，可从非 0 起 | 收藏状态增量：从上次已查末尾 `statusEnd` 到当前 items.length |

两者都按 `chunkSize`（默认 1000）切片。

### 3.2 并发池：worker 自取下一个任务

```
results: [R0, R1, ..., Rn-1]    ← 按入参下标存结果
next: 0                         ← 「下一个待处理下标」原子指针

worker 0 ── while next < n: i = next++ → fn(items[i]) → results[i] = 结果
worker 1 ── 同上
worker 2 ── 同上

await Promise.all([worker0, worker1, worker2])
→ results 按顺序填满
```

要点：
- `next++` 是单线程 JavaScript 里的原子操作（V8 不会在中间切线程），无需锁。
- 结果按 `i` 写入 `results[i]`，**与谁先完成无关**，最后返回的数组顺序与输入一致。
- 并发数取 `min(concurrency, items.length)`，避免 2 个任务开 5 个空 worker。

## 4. 关键代码对比与注释

### 4.1 `libraryWordsListPrefetch.ts`（新建，纯新增）

**来源**：`apps/frontend/src/views/englishLearning/library/utils/libraryWordsListPrefetch.ts`（当前，全文 L1–L63）

```typescript
/** 与后端 vocabulary/classic items API limit 上限一致 */
// 后端 items / favorites-status 接口都把 limit 最大值 clamp 到 1000；此处对齐以尽量利用单次请求
export const LIBRARY_ITEMS_FETCH_CHUNK = 1000;

// 单块结构：offset 是起始条目下标，limit 是取多少条
export type LibraryPrefetchChunk = { offset: number; limit: number };

/** 从 0 到续读页末尾需要的分页请求（尽量少次 HTTP） */
// 入参：resumeOffset = 跨会话保存的上次读到哪（页起点），pageSize = 单页条数
export function buildLibraryPrefetchChunks(
	resumeOffset: number,
	pageSize: number,
	// 自定义块大小（默认 1000）；单元测试或特殊场景可覆盖
	chunkSize = LIBRARY_ITEMS_FETCH_CHUNK,
): LibraryPrefetchChunk[] {
	// 窗口末尾 = max(至少 1 页, 续读起点 + 再往后 1 页)
	//   - resumeOffset=0 时 end ≥ pageSize：保证至少拉一页（不会空数组）
	//   - resumeOffset=3000, pageSize=100 时 end=3100：正好覆盖续读页 + 往后 1 页
	const end = Math.max(pageSize, resumeOffset + pageSize);
	// 整个窗口能塞到一个 chunk 内：只发 1 次请求
	if (end <= chunkSize) {
		return [{ offset: 0, limit: end }];
	}
	// 超过 1 个 chunk：从 0 开始逐块切片
	const chunks: LibraryPrefetchChunk[] = [];
	// i 每次 += chunkSize（1000）
	for (let offset = 0; offset < end; offset += chunkSize) {
		chunks.push({
			// 块起点
			offset,
			// 块大小：最后一块可能不满（end - offset < chunkSize）
			limit: Math.min(chunkSize, end - offset),
		});
	}
	return chunks;
}

/** [fromOffset, toExclusive) 按 chunk 切片，用于 items / favorites-status 对齐预取 */
// 入参：fromOffset = 从哪条开始（含），toExclusive = 到哪条结束（不含）
export function buildLibraryRangeChunks(
	fromOffset: number,
	toExclusive: number,
	// 自定义块大小
	chunkSize = LIBRARY_ITEMS_FETCH_CHUNK,
): LibraryPrefetchChunk[] {
	// 非法范围（空或负长度）：返回空数组（调用方据此短路）
	if (toExclusive <= fromOffset) return [];
	const chunks: LibraryPrefetchChunk[] = [];
	// 从 fromOffset 开始，逐块切片
	for (let offset = fromOffset; offset < toExclusive; offset += chunkSize) {
		chunks.push({
			// 当前块起点
			offset,
			// 当前块大小：最后一块 clamp 到 toExclusive
			limit: Math.min(chunkSize, toExclusive - offset),
		});
	}
	return chunks;
}

/** ponytail: 限制并发，避免续读很深时瞬间打满连接 */
// 泛型：T = 入项类型（通常是 LibraryPrefetchChunk），R = 返回类型（通常是 HTTP 结果）
export async function mapWithConcurrency<T, R>(
	// 要处理的项数组
	items: readonly T[],
	// 最大并发数（比如 3）
	concurrency: number,
	// 处理函数：(item, index) => Promise<R>
	fn: (item: T, index: number) => Promise<R>,
): Promise<R[]> {
	// 空数组：直接返回空（避免创建无意义的 worker）
	if (items.length === 0) return [];
	// 结果数组：长度与 items 一致，初始空槽
	const results: R[] = new Array(items.length);
	// 「下一个待处理下标」原子指针（单线程 JavaScript = 无竞争）
	let next = 0;
	// 启动 N 个 worker：N = min(并发上限, 任务数)，避免任务少时启动多余 worker
	const workers = Array.from(
		{ length: Math.min(concurrency, items.length) },
		// 每个 worker 是一个永不放弃的 async 函数：只要还有任务就自己抢 next
		async () => {
			// 循环：直到所有任务都被抢走（next >= items.length）
			while (next < items.length) {
				// 抢一个下标（后置 ++ = 先取旧值再自增，天然保证每个 i 只被一个 worker 拿到）
				const i = next++;
				// 执行处理函数，并按 **原下标** 写入 results[i]，保证顺序
				results[i] = await fn(items[i], i);
			}
		},
	);
	// 等待所有 worker 都跑完（它们会各自在 while 条件不满足时自然结束）
	await Promise.all(workers);
	// 返回按原顺序填好的 results
	return results;
}
```

## 5. 兼容性与影响

| 项 | 说明 |
| --- | --- |
| 破坏性 | 无。新建工具模块，不影响现有代码路径；仅新增文件 + 新增调用 |
| chunkSize 与后端 | `LIBRARY_ITEMS_FETCH_CHUNK = 1000` 与 controller/service 中 `Math.min(1000, limit)` 写死的上限强耦合。若后端上限下调，需同步改此常量，否则最后一个 chunk 拉 1000 会被后端 clamp 到更小（不报错，但会少拉数据） |
| 异常传播 | `mapWithConcurrency` **不 catch**：任何一个 `fn` 抛错都会让 `await Promise.all(workers)` 整体 reject。调用方（`useIncrementalVocabFavoriteStatus` 等）自行 try/catch 做回滚。这是故意的：单个失败 → 整块失败 → 下次重试，而不是静默丢掉某些 range 导致永远不查 |
| 并发数调优 | 当前单词库/经典句库并发都写死 3。后续可考虑：根据网络状况（慢网降低并发、HTTP/2 提高并发）动态调整，或按服务端能力做成常量 |
| 「ponytail」标识 | 代码注释中提到的 ponytail 是并发池常见写法：一组 worker 循环抢 next；语义等同于 Node.js `async.queue` / p-limit，但**不引入第三方依赖** |
