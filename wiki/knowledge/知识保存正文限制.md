---

## 1. 背景与目标

**用户现象**：已登录用户在知识库点击保存（`POST /api/knowledge/save`）时，正文略大（约 100KB 以上）会失败，后端日志出现 `PayloadTooLargeError` / `request entity too large`，前端表现为保存失败。

**根因**：NestJS / Express 默认 JSON 请求体上限为 **100KB**；而 `SaveKnowledgeDto` 与 `UpdateKnowledgeDto` 中 `content` 字段校验允许最大 **5,000,000 字符（约 5MB）**，二者不一致。

**目标**：将 HTTP 层 body parser 上限提高到与 DTO 一致的量级，使用户能正常保存中等篇幅的 Markdown 到云端。

## 3. 实现思路

1. **保持 `rawBody: true`**：Stripe Webhook 签名校验依赖原始请求体，不能在 `NestFactory.create` 时关闭 body parser。
2. **使用 `app.useBodyParser`**：NestJS 官方推荐在 `NestExpressApplication` 上调用 `useBodyParser('json', { limit })`；该方法会**尊重**已有的 `rawBody` 配置，不会破坏 Webhook 的 `verify` 回调。
3. **上限取 6MB**：DTO 允许 `content` 最长 5MB；JSON 序列化后还有 `title`、`author` 等字段与转义开销，故设为 **6mb**，略大于业务上限即可。
4. **同时配置 urlencoded**：与 json 保持一致，避免少数表单类请求踩到 100KB 默认线。
5. **生产 Nginx**：仓库内 `docs/ops/Nginx配置.md` 已配置 `client_max_body_size 100m`，反向代理层通常不是瓶颈；若自建部署未同步该配置，需另行调大。

**未采用**：按路由单独放宽（如仅 `/api/knowledge/save`）——改动面更大，且其它 JSON 接口（更新知识、批量操作等）同样可能携带大正文，全局 6MB 更简单且与 DTO 一致。

## 4. 关键代码与注释

### 4.1 启动时注册 body parser

**来源**：`apps/backend/src/main.ts`（约 L15–L25）

```typescript
async function bootstrap() {
	const app = await NestFactory.create<NestExpressApplication>(AppModule, {
		cors: true,
		// Stripe Webhook 需要原始 body；不能关掉 bodyParser
		rawBody: true,
	});

	// 说明：Express 默认 json 上限 100kb；知识库 content 允许至 5MB（见 SaveKnowledgeDto）
	// useBodyParser 会保留 rawBody 的 verify 逻辑，与 Stripe 兼容
	app.useBodyParser('json', { limit: '6mb' });
	app.useBodyParser('urlencoded', { limit: '6mb', extended: true });

	const uploadsRoot = getUploadsRoot(__dirname);
	// ... 后续中间件与 listen
}
```

### 4.2 DTO 业务上限（对齐依据）

**来源**：`apps/backend/src/services/knowledge/dto/save-knowledge.dto.ts`（约 L4–L12）

```typescript
export class SaveKnowledgeDto {
	@IsOptional()
	@IsString()
	@MaxLength(200)
	title?: string;

	@IsString()
	@MaxLength(5_000_000) // 说明：业务层允许单篇正文最多约 5MB 字符
	content!: string;
	// ...
}
```

`UpdateKnowledgeDto` 中 `content` 同样为 `@MaxLength(5_000_000)`。

## 5. 兼容性与影响

| 项 | 说明 |
|----|------|
| 行为变化 | 云端新建/更新知识时，正文可达约 5MB（受 DTO 校验约束） |
| 破坏性 | 无；仅放宽此前误拒的请求 |
| Stripe Webhook | `rawBody: true` 保留，不受影响 |
| 内存 | 单次请求解析上限 6MB，与知识库场景匹配；远低于 Nginx 上传 100MB 配置 |
| 本地模式 | 走 Tauri 写盘，不经此 HTTP 限制 |

**错误码说明**：修复前 `PayloadTooLargeError` 经全局 `AllExceptionFilter` 以 **500** 返回；属历史行为，本篇未改过滤器。若需对用户返回 **413**，可另开任务在 filter 中识别该异常类型。

---

## 6. 风险与回归建议

1. **重启后端**后，用约 110KB 正文的 Markdown 执行云端保存，应成功。
2. 接近 5MB 的正文：应通过保存；超过 DTO 上限应得到校验错误（非 `PayloadTooLargeError`）。
3. Stripe 测试 Webhook（若有）：确认签名校验仍通过。
4. **自建 Nginx**：确认 `client_max_body_size` ≥ 6m（仓库模板为 100m）。
